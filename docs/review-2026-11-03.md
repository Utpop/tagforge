# TagForge 功能有效性与一致性审查报告

审查对象：TagForge 0.2.1（commit `d0c611f`）
审查日期：2026-11-03
审查方式：静态阅读全部 3535 行源码 + 可复现探针 `tests/review_probe.py`（37 项断言）+ 现有 65 项测试回归

---

## 1. 审查范围

| 层 | 文件 | 行数 | 审查重点 |
|---|---|---|---|
| L0 契约 | `tagforge/fields.py` | 98 | 字段集合、patch 语义、数值规范化 |
| L1 适配 | `tagforge/adapters.py` | 707 | 四引擎读写对称性、帧级保留、封面处理 |
| L2 引擎 | `tagforge/naming.py` | 258 | 模板正反向一致性、占位符合法性 |
| L3 用例 | `tagforge/library.py` | 412 | 扫描边界、快照/回滚/撤销、重命名计划 |
| L4 表现 | `tagforge/gui.py` | 1564 | 状态机、控件有效性、预览/执行一致性、文案与行为 |
| 测试 | `tests/*.py` | 485 | 覆盖率、断言有效性 |
| 文档 | `README.md`、`docs/*.md` | — | 承诺与实现是否一致 |

**不在范围内**：DPI 渲染的像素级还原（已在此前验收）、音频编码正确性、跨平台（代码只支持 Windows 的 DPI/字体路径）。

## 2. 判定标准

一条功能判定为「按预期工作」需同时满足六条，任一不满足即计为缺陷：

- **S1 可达**：GUI 里存在能触发该能力的入口，且入口不是死控件。
- **S2 有效**：触发后产生的结果与控件标签描述一致（不是"点了没反应"或"反应了但不是这件事"）。
- **S3 保真**：往返（读→写→读）不丢失、不改变用户数据；不触碰未指定字段。
- **S4 对称**：同一语义在不同格式/不同入口下行为一致；不一致必须有明确理由。
- **S5 自洽**：界面文案、统计数字、按钮可用态与实际执行结果一致。
- **S6 鲁棒**：单个文件异常不扩散；异常必须显式报告，不得静默丢弃。

## 3. 结论摘要

| 级别 | 数量 | 含义 |
|---|---|---|
| **P0 不可用 / 数据损坏** | 9 | 界面整体失效，或写坏标签、撤销时清空文件标签 |
| **P1 功能失效** | 13 | 控件无效、流程可被绕过、失败后状态丢失 |
| **P2 一致性缺陷** | 20 | 界面与状态不符、跨引擎不一致、文档与实现矛盾、测试卫生 |

> **最高优先级**：P0-0——只要打开并关闭过任意一个对话框，主窗口就会永久变空白且所有交互失效。这不是边角情形，而是"生成 / 改名 / 撤销"三个主功能的必经路径。修复前，这三个功能实际上不可用。

**总体判断**：架构分层（fields → adapters → naming/library → gui）是成立的，patch 增量语义、模板双向同源、单文件失败回滚这三个核心设计在单点测试下都工作正常。但**批量/多文件路径上的边界处理明显弱于单文件路径**——本报告 42 项缺陷中，绝大多数只在"多文件、异常文件、快照失败、跨引擎、对话框往返"这些组合场景下暴露，而现有 65 项测试恰好全部避开了这些组合。

## 5. P0：不可用与数据损坏级缺陷

### P0-0 关闭任意对话框后，主窗口变空白且所有交互失效

**位置**：`gui.py:379`（主窗口设置 `Painter.current = self.p`）、`gui.py:1133`（对话框覆盖 `Painter.current = self.p`）、`gui.py:1162-1167`（`Dialog.close()` 不恢复）

```python
# 主窗口初始化
Painter.current = self.p

# 对话框初始化（覆盖全局）
Painter.current = self.p

def close(self):
    self.destroy()        # ← 没有把 Painter.current 还原成主窗口的 painter
```

而所有图标绘制函数都走这个全局：

```python
def icon_folder(x, y, color=FAINT):
    c = Painter.current          # 指向已销毁的对话框画布
    c.line(...)                  # TclError: invalid command name
```

**证据**（真实窗口，非模拟）：

```
打开并关闭「生成」对话框后：
  Painter.current 指向已销毁的对话框画布 = True
  重绘   → 崩溃 TclError
  排序   → 崩溃 TclError
  勾选   → 崩溃 TclError
  画布剩余元素 = 9（正常应为 398）    ← 界面几乎全空
```

截图确认：整个窗口只剩顶栏一条、路径框、四个批量输入框的位置标记，表格、详情面板、按钮、表头全部消失，且后续任何点击都不再有反应。

**影响**：**三个主功能（生成 / 改名 / 撤销）全部走对话框，所以只要用过一次其中之一，程序就变成一块空白的死界面**，必须重启。而且崩溃发生在 `redraw()` 内部——它先 `canvas.delete("all")` 再逐层绘制，抛错时界面已经被清空，用户看到的是"点一下，窗口没了"，没有任何错误提示（异常被 Tk 的回调机制吞进 stderr）。

**为什么测试没抓到**：`test_gui.py` 直接调用 `app.save()` / `app.apply_batch()`，从不经过对话框；截图验收时对话框是"打开着"的状态，没测"关闭之后"。

**修复**（两行）：

```python
class Dialog:
    def close(self):
        try:
            self.grab_release()
        except tk.TclError:
            pass
        Painter.current = self.app.p      # ← 归还给主窗口
        self.destroy()
```

更稳妥的做法是彻底去掉这个全局——给 `icon_*` 函数加 `painter` 参数，或改成 `Painter` 的实例方法。全局可变状态在这里没有任何收益，只带来了这一个致命缺陷。

**验证**：打开任一对话框 → 关闭 → 断言 `app.redraw()` 不抛错且 `len(canvas.find_all()) > 300`。

### P0-1 写封面会删除文件里其它所有图片帧

**位置**：`adapters.py:272-277`（ID3）、`adapters.py:388-404`（Vorbis）、`adapters.py:517-527`（MP4）、`adapters.py:600-609`（APEv2）

```python
if cover == "remove":
    tag.delall("APIC")
elif isinstance(cover, Cover) and not (mode == "fill" and tag.getall("APIC")):
    tag.delall("APIC")          # ← 删掉全部图片帧，而不只是封面
    tag.add(APIC(..., type=3, ...))
```

**证据**：一个含 3 张 APIC（封面 type=3、封底 type=4、艺人照 type=8）的文件，写一次封面后只剩 1 张：

```
写入前 3 张 → 写入后 1 张，types=[COVER_FRONT]
```

**影响**：用户单独改封面，封底和艺人照被永久删除。这直接违反 README 第 55 行「只写填了内容的字段，其余标签帧原样保留」的承诺，也违反 `research-and-plan.md` 结论 2。

**修复**：只删除 `type == 3` 的帧，保留其余类型：

```python
pics = tag.getall("APIC")
keep = [p for p in pics if getattr(p, "type", 0) != 3]
tag.delall("APIC")
for p in keep:
    tag.add(p)
tag.add(APIC(...))
```
Vorbis/MP4/APEv2 同理，只替换 front cover 一项。`remove` 也应只删 type=3。

**验证**：新增用例——写入 3 张 APIC 后改封面，断言张数仍为 3 且 type=4/8 的内容未变。

### P0-3 快照读取失败的文件，撤销时会被清空全部标签

**位置**：`library.py:132-138`（快照容错）、`library.py:280-285`（undo）

```python
# 快照：读取失败时记下空字段
except Exception as exc:
    entries.append({"path": path, "fields": {}, "cover": None, "error": str(exc)})

# undo：空字段 = 每个字段都写 None = 删除
patch = {key: entry["fields"].get(key) for key in FIELD_KEYS if key != "cover"}
patch["cover"] = cover if cover else "remove"
adapters.write_tags(path, patch, mode="overwrite")
```

**证据**：模拟"快照时文件被占用"（`read_record` 抛 OSError），随后 undo，标签从 `{'title': '必须保留', 'year': '2010'}` 变成 `{}`。

**影响**：**这是全项目最危险的缺陷。** 一个只是临时被占用的文件，只要它出现在某次批量操作的快照里，之后任何一次撤销都会把它所有 canonical 标签（标题/艺术家/专辑/年份/音轨/流派/作曲/备注/封面）删干净。快照失败本应降级为"该文件不参与撤销"，实际却变成"该文件可被清空"。

**修复**：快照阶段记录 `ok: false` 的文件，undo 时跳过并计入 `failed`：

```python
if entry.get("error") or not entry.get("fields"):
    failed.append({"path": path, "error": "快照不可用，已跳过"})
    continue
```
同时 `_restore_one` 也要做同样判断。

**验证**：让 `read_record` 对某文件首次调用抛错，执行 snapshot → apply → undo，断言该文件标签不变。

### P0-4 模板不含目录分隔符而勾选"匹配相对路径"时，目录前缀被写成音轨号

**位置**：`library.py:304-309` + `naming.py:186-203`

`preview_from_names` 用 `use_path` 决定匹配对象（相对路径 vs 文件名），但模板本身可能不含 `/`。此时正则 `^(.+?) - (.+?)$` 会把整个路径前缀吃进第一个捕获组。

**证据**（真实落盘，非仅预览）：

```
模板: "%track:2% - %title%"    勾选: 匹配相对路径
目标串: Daft Punk/RAM/01 - Give Life Back to Music
parsed: {'track': 'Daft Punk/RAM/01', 'title': 'Give Life Back to Music'}
落盘 TRCK: "Daft Punk/RAM/01/13"     ← ID3 把第一个 / 当 n/total 分隔符
回读 track: "Daft Punk"
```

只含一层子目录的常见情形同样中招：

```
根目录/Some Album/01 - Real Song.mp3
guess_template -> %track:2% - %title%     （因为 rel.count("/") == 1，没加目录段）
落盘 TRCK: "Some Album/01"
```

**影响**：音轨号被写成路径字符串，后续任何按音轨排序/命名都会错乱。且预览表里它显示为普通值（琥珀色），用户难以察觉。

**修复**：两道防线同时加。

1. 匹配对象与模板形状必须匹配——模板不含 `/` 时强制用文件名匹配，或自动补上目录段：

```python
if use_path and "/" not in template_raw and target.count("/") >= 1:
    # 显式报错优于静默错解
    return {"error": "模板不含目录分隔符，无法按目录结构匹配"}
```

2. 数值字段加校验：解析出的值含 `/` 或非数字时拒绝写入并标红该行。

**验证**：模板 `%track:2% - %title%` + `use_path=True` + 二层路径，断言 `parsed["track"]` 要么是 `"01"`，要么该行被标记为解析失败。

### P0-5 APEv2 引擎静默丢弃音轨总数与碟号总数

**位置**：`adapters.py:536-547`（`APEV2_KEYS` 缺 `tracktotal` / `disctotal`）、`adapters.py:586-596`

**证据**：

```
写 {"track": "5", "tracktotal": "9"}  →  回读 {'track': '5'}      # tracktotal 消失，无报错
```

且读取方向也不拆 `n/m`：

```
文件里 Track="3/13"  →  回读 {'track': '3/13'}     # ID3/MP4 都拆成 3 + 13
```

**影响**：APEv2 用户的音轨总数在读写中丢掉；同名字段在不同格式下语义不同（比 P1 更糟，因为它不报错）。

**修复**：写入时若 `num` 与 `total` 同时存在，按 APEv2 惯例写成 `"n/m"`；读取时 `partition("/")` 拆开，与 ID3 保持一致。

**验证**：`.wv` 文件写 track=5/tracktotal=9，回读两字段均正确；读一个手工写入 `Track="3/13"` 的文件，断言拆成 3 和 13。

### P0-6 只设置"音轨总数"时，ID3 与 APEv2 丢值，Vorbis/MP4 保留

**位置**：`adapters.py:250-257`

```python
tag.delall(frame_id)
if num:                          # ← total 有值但 num 为空时，整帧不写
    text = f"{num}/{total}" if total else num
```

**证据**（同一操作，四种格式）：

```
t.flac -> tracktotal='12'    ✅
```

**修复**：`num` 为空但 `total` 有值时，写 `"/12"` 或按惯例写 `"0/12"`；或直接拒绝并提示"需先填音轨号"。

**验证**：四格式各写 `{"track": None, "tracktotal": "12"}`，断言 `tracktotal == "12"`。

### P0-7 ID3v2.3 文件的多值字段被 `/` 连接，往返语义改变

**位置**：`adapters.py:207`（保留 v2.3）、`adapters.py:226`（`text=split_values(value)`）

**证据**：

```
v2.4 文件写 artist="A; B" → 回读 "A; B"    ✅
v2.3 文件写 artist="A; B" → 回读 "A/B"     ❌   （v2.3 规范用 / 分隔多值）
```

**影响**：`"A; B"` 变成 `"A/B"`，再读回来是**一个**值而不是两个。用户的组合艺术家（`AC/DC`、`Simon & Garfunkel` 这类）会被反向拆错。演示库里所有 mp3 都是 v2.3，所以这个路径是默认路径。

**修复**：v2.3 下要么禁用多值（合并为单值并提示），要么按 v2.3 规范写 `"A/B"` 但读取时也按 `/` 拆分——两者必须成对，不能只做一半。

**验证**：v2.3 文件写 `"A; B"`，回读必须仍是 `"A; B"`（或明确报"v2.3 不支持多值"）。

### P0-8 撤销对多值不保真：单值里的分号被拆成两个值

**位置**：`library.py:127-138`（快照存的是 `"; ".join` 后的字符串）→ `library.py:280-284`（undo 原样回写）→ `adapters.py:226`（`split_values` 再拆）

**证据**：

```
原文件 TPE1 = ['A; B']（单值，内部含分号）
撤销后    TPE1 = ['A', 'B']（变成两个值）
```

**影响**：撤销不是"恢复原状"而是"恢复成一个近似值"。这与 F18「安全底账」的定位矛盾——用户点撤销是为了回到确定的状态。

**修复**：快照保存原始帧结构（`frame.text` 列表）而非 join 后的字符串；或用显式转义（把 `;` 写成 `\;`）。

**验证**：写入含分号的单值，snapshot→undo，断言 `frame.text == ['A; B']`。

## 6. P1：功能失效与流程漏洞

### P1-1「跳过目标已存在的文件」是死控件

**位置**：`gui.py:1343`（`self.skip_exist = True`）、`gui.py:1413`（调用 `plan_rename` 未传该参数）、`library.py:346`（签名里根本没有此参数）

**证据**：`plan_rename(items, template_raw, root, keep_dir=True)` —— 无 `skip_exist`。勾选与否，`preview()` 走同一路径，`apply()` 也无条件跳过 `error` 行。

**影响**：用户取消勾选后期待"覆盖同名文件"，实际仍然跳过。控件说谎。

## 8. 跨模块一致性专项

### 8.1 四引擎字段支持矩阵（实测）

| 字段 | ID3 | Vorbis | MP4 | APEv2 |
|---|---|---|---|---|
| 全部 12 个文本字段 | ✅ | ✅ | ✅ | ⚠️ 缺 tracktotal/disctotal |
| `n/m` 音轨号拆分 | ✅ | ✅（分键） | ✅ | ❌ 不拆 |
| 多值（artist/genre/composer） | ⚠️ 仅 v2.4 | ✅ | ✅ | ❌ 单值 |
| 只写 total | ❌ 丢失 | ✅ | ✅ | ❌ 丢失 |
| 封面替换 | ❌ 删其它图 | ❌ 删其它图 | ❌ 删其它图 | ❌ 删其它图 |
| 保留未知帧（歌词/TXXX） | ✅ | ✅ | ✅ | ✅ |

结论：**"四引擎行为一致"是文档里的设计目标，实测不成立**。差异集中在 APEv2（字段缺两项）与 ID3v2.3（多值、total）。

### 8.2 状态机一致性

设计文档定义 `record.fields / staged / checks / active` 四变量。实际实现存在三处违反：

1. `staged` 不只在"单元格编辑"里变，`scan()` 会整体清空它——而设计说"staged 是唯一可变层，只有保存成功才清空"。
2. `active` 被 `scan()` 强制重置为 `records[0]`，设计未定义此行为。
3. `checks` 被 `scan()` 清空，而设计说"批量条永远显示作用到几个文件"——清空后计数从"已选 8 个"跳回"当前文件 1 个"，视觉上像批量条失效。

### 8.3 文档与实现的矛盾（3 处）

| 文档承诺 | 实现 |
|---|---|
| README:55「只写填了内容的字段，其余标签帧原样保留」 | 写封面/备注会清空同类的其它帧（P0-1/2） |
| architecture.md:202「保存失败：staged 保留（不丢用户输入）」 | `save()` 无条件清空 staged（P1-5） |
| gui-spec.md:183「面板改字段 → 表格同步变脏」 | 面板无命中区，只读（P2-7） |
| gui-spec.md:182「危险/模板动作三段式，写入按钮在预览前不可用」 | 改模板可绕过预览（P1-3/4） |

## 12. 结论

**有效性**：单文件、单字段、happy path 上的实现质量高——patch 增量语义、模板双向同源、快照与单文件回滚三个核心设计都经受住了验证。65 项测试在这一范围内是可靠的。

**一致性**：不足主要集中在三处系统性偏差——

1. **"替换一项"被实现成"清空整类"**（APIC、COMM），这是 2 个 P0 的共同根因；
2. **"预览"与"执行"没有数据绑定**（两个对话框各有反向问题），使三段式约束形同虚设；
3. **多文件路径的状态管理弱于单文件**（scan 无差别清空 staged/checks/active），使批量与撤销交互出现数据丢失。

**风险排序**：P0-0（关闭对话框后界面全失效）> P0-3（undo 清空标签）> P0-1/2（丢封底/备注）> P1-6（吞未保存编辑）> P0-4（音轨号污染）> 其余。

**建议**：P0-0 是唯一一个"正常使用必触发"的缺陷，应最先修；修它只需 2 行。在全部修复前，用真实音乐库时避开这些操作——"生成/改名/撤销任一功能一经使用就要重启程序""对只读/被占用文件做批量后撤销""批量改封面/备注""未保存单元格改动时执行批量"。完成第一批 6 项修复即可消除"界面失效"与全部数据损坏路径。

- **ID3v2.3 无法真正表达多值**：v2.3 用 `/` 分隔，与 `AC/DC` 这类含斜杠的单个艺术家冲突。
